1. Test Strategy
RoadMate is built test-first: acceptance criteria are written alongside each functional requirement in the PRD, and automated coverage is added in the same pull request as the feature, not after. This document defines the testing pyramid, environment strategy, and a representative test-case catalog per phase; the full case set should be maintained as living Playwright specs in the repository rather than a static document once Phase 1 reaches staging.

1.2 Environment strategy
Preview: Playwright E2E smoke suite runs against every pull request's Vercel preview deploy.
Staging: full regression suite plus load and security testing before each release candidate.
Production: post-deploy smoke suite (read-only checks + a synthetic non-destructive booking in Phase 2+) plus ongoing synthetic monitoring.
1.3 Release gate
A release is eligible for production promotion only when: all Must-priority FR test cases pass, no open Sev-1/Sev-2 defects, the E2E smoke suite is green on staging, and — from Phase 3 onward — the payment webhook reconciliation check has been manually verified for the release candidate.

4. Non-Functional Testing
4.1 Performance / load
Search endpoint: sustain the target concurrency (defined per launch-city sizing) with p95 response time under 2 seconds.
Booking-matcher function: verify correct behaviour under simulated concurrent booking submissions in the same micro-area, to catch race conditions in worker assignment.
Load test tooling: k6 scripts checked into the repository, run against staging before each major release.
4.2 Accessibility
Automated axe-core scan on every core screen in the Playwright suite; zero critical/serious violations allowed to merge.
Manual keyboard-navigation and screen-reader pass on the core Customer journey once per release.
4.3 Security testing
RLS policy tests: attempt cross-user data access for every table with a policy, confirm denial.
OWASP ZAP baseline scan against staging before each release.
Payment webhook signature verification test: reject unsigned/forged webhook payloads.
Admin route access tests: confirm role-gating for Admin vs. Super Admin scoped actions (e.g. city configuration).

5. Playwright Automation Framework
5.1 Structure
`/tests/e2e/customer/` — search, detail, review, booking, tracking, payment, rating specs
`/tests/e2e/worker/` — registration, availability, job-response, active-job specs
`/tests/e2e/admin/` — listings, moderation, worker-verification, analytics specs
`/tests/api/` — direct Supabase REST/RPC and Edge Function contract tests
`/tests/fixtures/` — seeded test data (shops, workers, users) reset per test run via a dedicated test schema/project
5.2 CI integration
The full Playwright suite runs on every pull request against a preview deployment; a lighter smoke subset runs post-deploy against staging and production. Flaky tests are quarantined into a tracked list rather than silently retried indefinitely, to keep the signal trustworthy.
5.3 Regression suite ownership
Each new Must-priority FR ships with at least one E2E test in the same pull request. QA reviews and, where needed, extends coverage during sprint testing before a feature is marked release-ready.
