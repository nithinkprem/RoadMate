1. Purpose & Scope
This document translates the RoadMate PRD into an implementable system design: architecture, full data model across all four phases, API contracts, third-party integration flows, and deployment topology. It should be read alongside the PRD, which owns product rationale, and the UI/UX Specification, which owns screen-level detail.
2. Architecture Overview
2.1 Guiding principle
Keep Phase 1 server-less and cheap to operate, and introduce a dedicated application-server layer only where Supabase's built-in capabilities stop being sufficient — specifically for booking-matching logic, notification dispatch, live-tracking ingestion, and payment webhooks, all introduced from Phase 2 onward.

2.3 Data flow — core booking loop (Phase 2+)
Customer submits a booking via the web client → API request to a Supabase Edge Function (`create-booking`).
Function inserts a `bookings` row (status = requested) and queries `workers`/`worker_services` for the nearest N online, eligible workers.
Function enqueues notification payloads for those workers via the notification service.
Workers receive push notifications; first Accept response wins (optimistic locking on `bookings.worker_id`).
On acceptance, a notification is sent to the customer and the booking status transitions to accepted.
Worker's client posts periodic location updates to `tracking_events` (Phase 3), which the customer client subscribes to via Supabase Realtime.
On completion, a Razorpay order is created (Phase 3); the webhook handler updates `payments` and the booking ledger on success.

5. Integration Design
5.1 Google Maps Platform
Maps JavaScript API renders the results map and shop-detail static map.
Places API is used once, offline, to seed the initial Calicut shop directory; not called live per-search to control cost.
Directions API powers the "Navigate" action, opening native Google Maps with a pre-filled destination.
Distance calculation for ranking uses a server-side Haversine/PostGIS calculation against stored coordinates, not a live Directions call, to keep search latency and cost low.
5.2 Notifications (OneSignal/FCM)
Each booking-lifecycle transition (requested→accepted, accepted→arrived, etc.) publishes an event that the notification service maps to a push payload.
Delivery failures are retried with backoff; in-app notification list (FR notifications table) is always the source of truth, push is best-effort.
5.3 Payments (Razorpay)
One-time payments use Razorpay Orders + Checkout for per-job payment at completion.
Memberships use Razorpay Subscriptions for recurring annual billing.
All payment state changes are driven by verified webhook events, never by client-reported success, to prevent spoofed payment confirmation.
5.4 AI Diagnosis (Phase 4)
Image/audio classification can start as a hosted third-party model call (e.g. a vision/audio classification API) rather than a custom-trained model, to reach market faster; a proprietary model trained on RoadMate's own job-outcome data is a post-Phase-4 evolution.
Every prediction is logged to ai_diagnosis_logs with a confidence score and is always presented to the user as a suggestion the user can override, never an autonomous action.

6.1 CI/CD
GitHub Actions runs lint, type-check, unit tests, and the Playwright E2E suite against a preview deploy on every pull request. Merges to main auto-deploy to staging; production deploys are a manual promotion step gated on the QA sign-off checklist in the Test Plan companion document.
6.2 Observability
Error tracking via a hosted error-monitoring service (e.g. Sentry) wired into both the Next.js client and Edge Functions.
PostHog event tracking for product funnels (search → detail view → contact action → Phase 2+ booking → completion).
Structured logging on all Edge Functions with request IDs for traceability across the booking-matching flow.
